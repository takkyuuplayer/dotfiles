# GitHub Draft Evidence Review

GitHub 上のコメントで、diff や commit だけでは分からない「なぜそう判断したか」を読める状態にする。根拠は公式仕様などの一次情報、またはこのセッションでの調査・判断の経緯。コメント数ではなく、読み手の判断コストを下げる文脈の質を優先する。

## 境界

- 主な対象は作成済み PR の `Files changed` に置く review comment。issue コメント、PR の通常コメント、レビューコメントへの返信本文も、このセッションの経緯を GitHub に残す依頼なら扱う。
- GitHub への書き込みは `PENDING` review の作成まで。レビューを submit する API、`APPROVE`、`REQUEST_CHANGES`、`COMMENT` event は呼び出さない。issue / PR 通常コメントや返信は本文を作り、ブラウザに貼れる形で渡す。
- pending review の作成は外部への書き込みである。ユーザーがコメントを「追加する」「置く」「下書きとして作る」と依頼した場合だけ実行する。「案を見せて」「コメントを考えて」ならプレビューまでに留める。
- 一般的なコードレビュー、PR 本文の作成、diff から自明な実装説明は追加しない。

## コメント先の決め方

対象の種別で書き方と実行方法が変わる。曖昧なら、何に置くコメントかだけ確認する。

| 種別 | 扱い |
| --- | --- |
| Files changed の review comment | PR、HEAD SHA、diff 上の行を確定し、必要なら pending review を作成する |
| issue コメント | 課題への報告・提案として、背景を本文で短く補う |
| PR 通常コメント | レビュアー向けに、diff から読めない判断理由へ絞る |
| レビューコメントへの返信 | 「直した」か「直さない、理由は何か」を最初に出す |

対象の PR / issue が会話中に出てきていない場合、現在のブランチから当たりを付けて確認する:

```bash
gh pr view --json number,url,title,headRefOid
```

## Files changed に根拠を置く変更の選び方

PR 全体へ機械的にコメントを付けない。次のような、コード単体では判断理由を復元しにくい箇所を選ぶ。

- API・言語・ライブラリの仕様に合わせた実装
- 互換性対応、回避策、非自明な分岐や定数
- セキュリティ、アクセシビリティ、プロトコル上の要件
- 特定バージョンの挙動や、採用案と代替案の境界

コメントを置かなくても PR 本文やテストから十分理解できる箇所、同じ根拠の重複、変更と直接関係しない参考資料は除く。根拠を確認できない意図は推測で補わない。

## ワークフロー

1. ユーザー指定の URL / 番号、または現在のブランチに対応する `gh pr view` から対象を特定する。Files changed に置く場合は、PR のリポジトリ、番号、URL、`headRefOid` を記録する。
2. 根拠の種類を決める。公式仕様・API docs・ソース permalink などの一次情報を根拠にするなら [一次情報コメント](#一次情報コメント) に進む。このセッションでの調査や判断経緯を根拠にするなら [セッション由来コメント](#セッション由来コメント) に進む。
3. Files changed に置く場合は、PR 本文、commit、diff、周辺コード、テストを読み、コメント対象行が現在の unified diff に実在することを確認する。
4. コメント本文と配置先を組み立て、投稿前に全件を見直す。リポジトリの言語と署名規約に従う。
5. ユーザーが pending review の作成を依頼している場合だけ、後述のスクリプトで一括作成する。結果の `state` が `PENDING` であることを確認し、件数と PR URL を報告する。それ以外はワーキングツリー外に本文を書き出し、コピー用コマンドを提示する。

## 一次情報コメント

各判断点について一次情報を調べる。公式仕様・標準・RFC・公式 API ドキュメント・当該プロジェクトのソースコードや maintainer の release note を優先する。検索結果、まとめ記事、AI 生成文は根拠として使わない。

バージョンと該当箇所を直接示す安定した URL を選ぶ。ソースコードなら可能な限り tag または commit の permalink を使う。記述が変更へどう適用されるかまで確認する。

基本形は次のとおり。見出しは内容に合わせて省略してよい。

```markdown
<必要な署名>

根拠: [資料名 - 該当節](https://primary.example/spec#section)

> 原文からの短い抜粋

この変更では、上記の要件を満たすために `<変更の判断>` としています。
```

- 冒頭で一次情報へ直接リンクし、直後に関連部分だけを抜粋する。
- 抜粋は原文どおり、1 資料につき合計 25 語以内に留める。翻訳は引用に混ぜず、必要なら「要旨」と明記して言い換える。
- 最後の 1〜2 文で、資料の記述と対象行の関係を説明する。diff の言い換えではなく「この仕様だから、この選択」の接続を書く。
- 一つのコメントには一つの判断を載せる。複数行が一つの判断を構成するときだけ multi-line comment にする。
- リンク先が主張を直接支えていない、対象バージョンが違う、引用の前後で意味が変わる場合は使わない。

## セッション由来コメント

セッション中の会話は一次資料として扱えるが、会話ログそのものは成果物ではない。結論だけでは理由が落ち、ログを貼ると読まれない。本文は結論、折りたたみは背景を理解できる最小限のまとめにする。

### 会話ログを材料として取り出す

同梱スクリプトで transcript から会話を取り出す。思考ブロック・ツール呼び出し・ツール結果・system-reminder は自動で落ちる。

```bash
python3 <skill-dir>/scripts/extract_transcript.py --quote > "$TMPDIR/session-log.md"
```

主なオプション:

- `--list` - セッション一覧（日時と ID）を表示。別セッションの内容を引くときにまず使う
- `--session <id|path>` - 対象セッションの指定（既定は最新 = 通常は今のセッション）
- `--last-n <N>` - 末尾 N 発言だけ。長いセッションの終盤だけ引きたいときに
- `--since <ISO8601>` - 指定時刻以降の発言だけ
- `--include-sidechain` - subagent の会話も含める（既定は除外）
- `--quote` - Markdown の引用記法 `>` を付ける
- `--format json` - 発言単位の構造化出力。取捨選択を自分でやりたいとき

今のセッションを引く場合、transcript はライブで書かれているため、末尾にはこのスキルを起動した指示そのものが載ることがある。

### 背景へ凝縮する

会話ログを読み、それを読まなくても経緯が分かるまとめに書き直す。発言の羅列ではなく、地の文と箇条書きで。折りたたみを開いた人が 30 秒で追える量、目安 10〜20 行に収める。

含めるもの:

- 出発点。何が問題だったのか、何を頼まれたのか
- 途中で分かった、結論を左右した観察（数値・エラーメッセージ・仕様の制約など）
- 決めたことと、その決め手
- 検討したが採らなかった選択肢と、採らなかった理由

落とすもの:

- 結論に影響しなかった試行錯誤、ツール実行の失敗と再試行
- 誰がいつ何を言ったかという進行そのもの
- 投稿先のリポジトリと無関係な話題

発言をそのまま引用するのは、言い回し自体が根拠になるときだけにする。その場合も 1〜2 行に留め、まとめの中に埋め込む。

### 外に出せない情報を落とす

書き出す前に次を洗い出して、置き換えるか、その記述ごと削る。

| 出るもの | 対処 |
| --- | --- |
| 一時ディレクトリ（`/tmp/...`、`$TMPDIR` の展開結果、スクラッチパッドのパス） | 削るか `<tmp>/comment.md` のように伏せる |
| ホームディレクトリを含む絶対パス（`/Users/<name>/...`） | リポジトリ相対パスに直す |
| worktree の置き場所、ローカルブランチの試行錯誤 | 読み手に無関係なので削る |
| API キー・トークン・社内固有の URL・第三者の個人名 | 削る。迷ったら記述ごと落とす |

機械的な洗い出しには grep が早い:

```bash
grep -nE '/Users/|/tmp/|\$TMPDIR|/private/var/folders' "$TMPDIR/comment.md"
```

GitHub のコメントは削除しても編集履歴とメール通知に残る。投稿前が唯一の防波堤だと考えて扱う。

### 本文の組み立て

通常コメントやレビュー返信は次の構成で書く。Files changed に置く review comment では、対象行に必要な部分だけに短く縮めてよい。

```markdown
🤖 <agent> (<model>)

<結論・依頼・報告を 1〜3 文で。読み手が最初の 1 行で「自分が何をすべきか」を判断できるように>

## 経緯 / 根拠
<なぜこの結論になったかを箇条書きで数行。diff やコミット履歴を読めば分かることは書かない>

<details>
<summary>背景</summary>

<ここまでで書いたまとめ。10〜20 行>

</details>
```

- GitHub コメントは 1 行目に `🤖 <agent> (<model>)` を置く。
- 日本語で書く。リポジトリの既存 issue / PR が英語なら、それに合わせる。
- 本文と折りたたみで同じことを書かない。重複するなら本文側を削る。
- レビュー返信では `## 経緯 / 根拠` は不要なことが多い。「指摘のとおり修正した / この理由で修正しない」を明示し、必要な背景だけ折りたたみに入れる。

通常コメントや返信の本文はワーキングツリー外（`$TMPDIR` またはセッションのスクラッチパッド）に書き出し、コピー用コマンドを 1 つ提示する。

```bash
pbcopy < /tmp/xxx/comment.md
```

macOS 以外なら `xclip -selection clipboard <` や `wl-copy <` に読み替える。本文のプレビューと書き出したファイルのパスも伝える。

## Pending review の作成

[GitHub REST API](https://docs.github.com/en/rest/pulls/reviews#create-a-review-for-a-pull-request) では `event` を省略すると review が `PENDING` になる。一時 JSON をワーキングツリー外に作り、調査時に記録した PR の HEAD SHA を `commit_id` に入れる。一次情報コメントでもセッション由来コメントでも、Files changed に置く場合はこの形を使う。

```json
{
  "commit_id": "<40-character PR head SHA>",
  "comments": [
    {
      "path": "path/to/file.ts",
      "line": 42,
      "side": "RIGHT",
      "body": "根拠: [公式仕様](https://example.com/spec)\n\n> Short exact quote.\n\nこの変更との関係を説明します。"
    }
  ]
}
```

`line` は diff 上の blob 行番号を使う。追加行またはコンテキスト行は `RIGHT`、削除行は `LEFT`。複数行には `start_line` と `start_side` も指定する。[review comment API](https://docs.github.com/en/rest/pulls/comments#create-a-review-comment-for-a-pull-request) で廃止予定とされる `position` は使わない。

```bash
python3 <skill-dir>/scripts/create_pending_review.py \
  --repo OWNER/REPO \
  --pr NUMBER \
  --input "$TMPDIR/evidence-review.json"
```

スクリプトは次を投稿前に検証する。

- input に review を submit できる `event` や review 本文が含まれていないこと
- JSON の `commit_id` が現在の PR HEAD と一致すること
- 現在のユーザーによる pending review がまだ存在しないこと
- コメントが `path`、`line`、`side`、`body` を持つこと

既存の pending review がある場合は、新規 review を作らずユーザーへ報告する。POST の成否が不明な場合も自動で再試行せず、pending review の有無を一度確認して結果を報告する。レビューの submit は常にユーザーが GitHub 上で行う。
