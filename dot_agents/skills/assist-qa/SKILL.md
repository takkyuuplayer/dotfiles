# assist-qa

リリースに含まれるPRを調べ、人がコピペして使えるQAチェックリストを作成する。
特に指定がなければ、対象バージョンをデプロイしたstg環境での手動確認を前提にする。ユーザーが指定した環境・範囲・形式を優先する。

## 調査

- リリース本文から対象PRを列挙する。PRの本文・E2E手順・差分を必要な範囲で読み、実際の変更と画面名・表示条件・権限を把握する。
- 依存ライブラリやサービスの更新では、利用箇所や更新内容を確認して、影響する既存機能を選ぶ。参照先を取得できない場合は、確認できた範囲と不足情報を短く明記する。
- PR内のチェック済み項目は過去の検証結果として扱う。今回のstgで実施済みとは扱わない。

## 分類

各PRに次のいずれか1つを付ける。表記はこの3種類に統一する。

| 分類                   | 判断基準                                                                         | 手順の内容                                               |
| ---------------------- | -------------------------------------------------------------------------------- | -------------------------------------------------------- |
| 動作を確認             | 新機能、仕様変更、不具合修正など、意図した挙動を確認する変更                     | 変更された動作、再現条件、必要な権限・表示条件を確認する |
| 壊れてないことだけ確認 | 依存更新や内部変更など、利用者向けの挙動変更を意図しない変更                     | 影響する既存機能を代表的な操作で確認する                 |
| Skip                   | 開発用seed、CI、ビルド専用依存など、デプロイ後の対象環境で確認する操作がない変更 | スキップ理由を1文で書く。実行手順は付けない              |

- 依存更新という理由だけでSkipにしない。対象環境で動くコードやサービスへの影響を見て判断する。
- 「壊れてないことだけ確認」では、可能なら利用者が行う操作を記載する。バージョン・コンテナの稼働確認だけで機能の回帰確認を済ませたことにしない。
- 情報不足はSkipの理由にしない。根拠のある確認項目を作り、不足している点を注記する。

## 出力

- 日本語で、リリース内の全PRを掲載する。各項目のタイトルはPRタイトルを原文のまま使う。翻訳・短縮・QA向けの改題をしない。
- 各タイトルにPRリンクと分類を添える。原則としてリリース本文の順序を保つ。
- 操作手順と期待結果を未チェックのチェックリストで記載する。必要なテストデータ・アカウント・権限は短く添える。
- 各手順は「どの画面で、何を操作し、何が確認できればよいか」が分かる粒度にする。差分から読み取れない画面や挙動を作らない。
- 共通部品は代表画面を選び、変更の影響が異なる表示パターンは残す。関連しない網羅的なQAへ広げない。
- チャットでは、完成した一覧を1つのdocument writing blockにまとめる。修正時は同じブロックIDを使う。別の出力先を指定された場合はそれに従う。
- このスキルでは手順の作成までを行う。依頼されていないデプロイ・テスト操作・GitHub投稿は行わない。

出力例：

**PRの原文タイトル**  
[PR #123](https://github.com/owner/repo/pull/123)  
分類：**動作を確認**

準備：必要なテストアカウントやデータ。

- [ ] 対象画面を開く → 変更された操作を行う。期待する結果になること。

**別のPRの原文タイトル**  
[PR #124](https://github.com/owner/repo/pull/124)  
分類：**Skip**

開発環境専用の変更のため、stgでのQAは対象外。
