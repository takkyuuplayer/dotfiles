# GitHub Comment from Session

セッション中の会話を一次資料として、GitHub の issue / PR コメント・レビュー返信の本文を組み立てるスキル。

**なぜ会話ログを添付するのか**: 要約だけでは「なぜその結論になったか」が落ち、後から読む人が同じ検討をやり直すことになる。一方で会話全文を本文に貼ると長すぎて読まれない。だから **本文は要約、根拠は折りたたみ** という形をとる。

## ワークフロー

### Step 1: 投稿先を確定する

ユーザーの指示から、次の 3 つのどれかを特定する。曖昧なら聞く。

| 種別 | 必要な情報 | 投稿コマンド |
| --- | --- | --- |
| issue コメント | `<owner>/<repo>`, issue 番号 | `gh issue comment <n> -R <owner>/<repo> --body-file <path>` |
| PR コメント | `<owner>/<repo>`, PR 番号 | `gh pr comment <n> -R <owner>/<repo> --body-file <path>` |
| レビューコメントへの返信 | `<owner>/<repo>`, PR 番号, 返信先コメント ID | `gh api repos/<owner>/<repo>/pulls/<n>/comments/<comment_id>/replies -f body="$(cat <path>)"` |

番号が指定されていない場合、現在のブランチから推測する:

```bash
gh pr view --json number,url,headRefName
```

推測した番号は必ずユーザーに確認してから使う。誤爆すると無関係な PR に投稿されるため。

レビューコメント ID が分からない場合は一覧から探す:

```bash
gh api repos/<owner>/<repo>/pulls/<n>/comments --jq '.[] | {id, path, line, user: .user.login, body: .body[0:120]}'
```

### Step 2: 会話ログを抽出する

同梱スクリプトで transcript から会話を取り出す。思考ブロック・ツール呼び出し・ツール結果・system-reminder は自動で落ちる。

```bash
python3 <skill-dir>/scripts/extract_transcript.py --quote > "$TMPDIR/session-log.md"
```

主なオプション:

- `--list` — セッション一覧（日時と ID）を表示。別セッションの内容を引くときにまず使う
- `--session <id|path>` — 対象セッションの指定（既定は最新 = 通常は今のセッション）
- `--last-n <N>` — 末尾 N 発言だけ。長いセッションの終盤だけ引きたいときに
- `--since <ISO8601>` — 指定時刻以降だけ
- `--include-sidechain` — subagent の会話も含める（既定は除外）
- `--quote` — Markdown の引用記法 `>` を付ける
- `--format json` — 発言単位の構造化出力。取捨選択を自分でやりたいとき

**今のセッションを引く場合の注意**: transcript はライブで書かれているため、末尾にはこのスキルを起動した指示そのものが載る。読み手に無関係な部分は切り落とす。

### Step 3: 引用範囲を選ぶ

全部貼れば良いわけではない。折りたたみの中でも、次のものは削る:

- 試行錯誤の末に捨てられたアプローチ（結論に影響しないもの）
- ツール実行の失敗と再試行など、機械的なノイズ
- 投稿先のリポジトリと無関係な話題、ローカルパスや個人的な文脈

逆に必ず残すもの:

- 結論の根拠になった観察・数値・エラーメッセージ
- ユーザーが方針を決めた発言（「こっちでいく」「それはやめて」など）
- 検討したが採らなかった選択肢と、採らなかった理由

削った箇所は `> _(中略: 〜についての試行錯誤)_` のように明示する。無言で削ると引用の信頼性が落ちる。

### Step 4: 本文を組み立てる

次の構成で書く。

```markdown
🤖 <agent> (<model>)

<結論・依頼・報告を 1〜3 文で。読み手が最初の 1 行で「自分が何をすべきか」を判断できるように>

## 経緯 / 根拠
<なぜこの結論になったかを箇条書きで数行。diff やコミット履歴を読めば分かることは書かない>

<details>
<summary>Agent との会話ログ</summary>

<!-- extract_transcript.py の出力 -->

</details>
```

守るべき点:

- **1 行目に署名**。グローバルルールで、コメントは 1 行目に `🤖 <agent> (<model>)` を置くと決まっている（issue / PR 本文なら末尾）。モデル名はこのセッションを動かしている実際のモデル ID を書く
- **簡潔に**。diff やコミット履歴から読めることは書かない。書くのは「なぜ」と、コードからは読めない文脈だけ
- **日本語**。リポジトリの既存 issue / PR が英語なら、それに合わせる（`gh issue list` などで確認）
- レビュー返信の場合、`## 経緯 / 根拠` は不要なことが多い。「指摘のとおり修正した / この理由で修正しない」を明示し、根拠だけ折りたたみに入れる
- 会話ログ内に API キー・トークン・社内固有の URL・個人名が含まれていないか投稿前に確認する。GitHub のコメントは削除しても履歴やメール通知に残る

### Step 5: ファイルに書き出して gh コマンドを提示する

本文はワーキングツリー外（`$TMPDIR` またはセッションのスクラッチパッド）に書き出す。リポジトリを汚さないため。

そのうえで **コマンドは実行せず、ユーザーが実行する形で提示する**。投稿は取り消しの効かない外向きの操作であり、最終確認はユーザーが行う。

提示するときは、本文のプレビュー（少なくとも折りたたみの外側部分）と、コピーしてそのまま実行できるコマンドを 1 つ出す。`-R <owner>/<repo>` を必ず付け、どのディレクトリからでも動くようにする。

```bash
gh pr comment 42 -R takkyuuplayer/dotfiles --body-file /tmp/xxx/comment.md
```

## 例

**入力**: 「いまの調査を #17 にコメントしといて」

**出力する本文**:

```markdown
🤖 Claude Code (claude-opus-5)

pre-push フックが遅い原因は、新規ブランチのとき `@{u}..HEAD` が解決できず全履歴を検査していたことでした。マージベースを使う形に直せば解消します。

## 経緯 / 根拠
- upstream 未設定のブランチでは `git rev-list @{u}..HEAD` が全コミットを返す
- 手元の計測で 1,800 コミット走査 → 修正後は 3 コミット
- `--not --remotes` 案も検討したが、複数リモート環境で取りこぼすため不採用

<details>
<summary>Agent との会話ログ</summary>

> **user**
>
> push が異常に遅いんだけど
...

</details>
```
